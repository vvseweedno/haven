# Security and Data Boundaries

This is a local research implementation, not an independently audited node or a production identity service. The source specification's audit label does not certify this implementation.

## Threat Model

The implementation aims to prevent accidental publication of private notebook data, detect encrypted archive tampering, reject bounded malformed input, and reduce script injection and framing exposure. It does not protect a compromised OS, browser, extension, supply chain or already executing same-origin JavaScript. No server-side identity, authorization or multi-user storage exists.

The local server binds to `localhost:41731`, not all network interfaces. Use the same origin consistently: `127.0.0.1`, `localhost`, other ports and HTTPS have distinct browser storage. The two read-only API endpoints contain curated fixtures, not private data.

## Private Notebook

- AES-GCM with a 256-bit, nonextractable Web Crypto key and a fresh random 96-bit IV per save; 128-bit authentication tag.
- PBKDF2-HMAC-SHA256 with 600,000 iterations and a random 128-bit salt per notebook. Passphrases are 12-256 characters; a long unique phrase remains essential against offline guessing.
- Fixed versioned authenticated additional data binds the cryptographic format. Salt changes produce authentication failure; unsupported algorithms and work factors are rejected before key derivation.
- Titles, bodies, kinds, identifiers and timestamps all live inside the ciphertext. Only algorithm descriptors, salt and IV remain visible.
- Strict archive and note bounds: 3 MB import, 2 MB plaintext before encryption, 100 notes, 120-character titles and 20,000-character bodies. The input is JSON, never executable code.
- Only encrypted archives are exported. Imports require decryption and a separate replacement confirmation. There is no plaintext export or upload endpoint.
- Archive writes use Web Locks to serialize snapshot comparison and storage across cooperating tabs. A browser without Web Locks can read/export an archive but cannot write it. Other-tab storage changes lock the session. A failed storage write leaves the editor marked unsaved and the previous archive unchanged.
- Reload/navigation locks the notebook. An inactivity check runs every 10 seconds and locks after 5 minutes without key/pointer interaction. It attempts to save dirty notes first. If that fails, it locks and reports that the last edits were not saved. Browser timer throttling can delay the check in background tabs; this is not an OS screen lock.
- Normal navigation warns about unsaved edits. Back/forward, crashes, forced termination and browser policy can still discard unsaved input. Explicit saves and encrypted backups are required for durable use.
- Unlocked content and keys reside in browser memory. Clearing references is not guaranteed memory zeroization in JavaScript. Browser password managers operate independently of this app.
- There is no password recovery, key escrow, account synchronization, agent credential storage or durable agent identity claim.

## HTTP and Input Controls

- A request-specific nonce is generated by Next.js Proxy. Incoming nonce headers are overwritten. The nonce is applied to the trusted theme script and framework scripts.
- Production `script-src` uses a nonce and `strict-dynamic`, without `unsafe-inline` or `unsafe-eval`; script attributes are blocked. Inline styles remain allowed for graph layout.
- Frames, object plugins, external form submissions and external connection targets are restricted. MIME sniffing is disabled. Browser camera, microphone, geolocation, payment and USB permissions are disabled.
- `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin` are sent. No permissive CORS headers are added.
- Next Image accepts only local `/assets/**` paths. No third-party fonts, media, analytics or runtime fetch dependencies are used.
- Catalog parameters reject unknown/repeated keys, control characters, unsupported kinds, excessive query length, invalid limits and offsets. A process-wide token budget limits catalog computation; it is neither per-client nor distributed protection.
- API responses have explicit public cache policy and ETags. Error responses are not cached. The notebook is not part of the API module or public search index.
- The object inspector computes SHA-256 over exact UTF-8 input bytes. It does not canonicalize JSON, verify signatures, validate the HAVEN protocol or establish trust from a visibility declaration. Reports omit source values.

## Performance Tradeoff

Nonce-based script protection requires dynamic HTML rendering, so HTML is private/no-store rather than shared static output. This is deliberate. Hashed build assets and optimized images remain cacheable; public JSON supports 30-second freshness, 120-second stale-while-revalidate and conditional 304 responses. Sidebar prefetching is disabled and global search code/data load only when opened.

## Before Public Deployment

Perform an independent code and cryptography review. Add HTTPS and HSTS at the TLS edge, deployment-specific origin configuration, distributed abuse controls, resource limits, logs without private payloads, alerting, backup/recovery drills and dependency monitoring. Do not enable HSTS blindly on the HTTP-only local preview. Real agent admission needs a separately designed authentication, authorization, key lifecycle and persistence system. Do not expose the local demo by changing the bind address and calling it production-ready.

## Verification

```bash
npm ci
npm test
npm run build
npm start
python scripts/test-ui.py
python scripts/test-security-ui.py
npm audit
```

The browser security suite injects unauthorized code into intercepted HTML response bytes with CSP enforcement enabled. Debugger-created scripts are not an equivalent test of untrusted HTML. It also exercises storage failures, cross-tab changes, encrypted recovery, API contracts, privacy boundaries and mobile layouts.

Reference guidance: [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html), [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), and the Next.js CSP guide shipped with the installed package. An `npm audit` result is a point-in-time dependency check, not proof of application security.
